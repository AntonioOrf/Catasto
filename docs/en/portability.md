## 1. Purpose and audience

The portal is to be moved to a university's servers, with technologies not yet known. This document is for the project team and for the IT service that will host it. It lists what the portal requires of any platform (§2), how to install it in the most likely cases (§3), what changes when several instances run (§4), the questions to ask the university (§5) and how to transfer the data (§6). Installation with Docker Compose remains described in [Installation and deployment](installation.md), environment variables in [Backend and API](backend.md), §9.

---

## 2. Portal requirements

The portal is **a single Node.js process** serving both the site and the API, plus a **MySQL database**. It writes no files to disk and holds no state of its own beyond the database.

| Requirement | Detail |
|---|---|
| Runtime | Docker image `ipavon/catasto1427` (Node 20 Alpine, unprivileged user `1000`), or Node.js ≥ 20 without containers |
| Port | One internal HTTP port (`PORT`, default `3005`); HTTPS is provided by the proxy in front |
| Database | MySQL 8 (tested) or TiDB (in use on Vercel); MariaDB to be verified (§3.5). About 61,000 *fuochi* (households) and 270,000 family members |
| Filesystem | Read-only: nothing is written while running |
| Outbound network | `archiviodigitale-icar.cultura.gov.it` (IIIF manifests, queried by the backend); `formsubmit.co` (user report emails, optional). Folio images are downloaded directly by the user's browser |
| Indicative resources | 0.1–0.5 CPU, 256 MB of RAM at rest, up to 1 GB during the largest Excel exports |
| Secrets | Database credentials, `SEGNALAZIONI_SALT`, `ADMIN_TOKEN`, `MODERAZIONE_SECRET` |
| Health checks | `/health/live` (the process responds) and `/health/ready` (the database responds): [Backend and API](backend.md), §4.17 |

## 3. Installation scenarios

### 3.1 Virtual machine with Docker

This is the case already documented: follow [Installation and deployment](installation.md), §3. If the university's HTTPS proxy sits in front of the container and port `1427` is not reachable from outside, set `TRUST_PROXY=1`.

### 3.2 Virtual machine with Podman

Common on Red Hat distributions (RHEL, Rocky, Alma). The same `docker-compose.yml` works with `podman compose` (or `podman-compose`). Differences to know:

- images must be given with the full registry if the university does not have `docker.io` among its search registries (`docker.io/ipavon/catasto1427:latest`, `docker.io/library/mysql:8.0`);
- with SELinux enabled, mounted volumes need the `:Z` suffix (`./mysql_data:/var/lib/mysql:Z`);
- for start at boot, use a systemd unit generated by Podman (Quadlet or `podman generate systemd`) instead of `restart: always`.

### 3.3 Kubernetes or OpenShift

The [`deploy/kubernetes/`](../../deploy/kubernetes) folder contains base manifests for a database outside the cluster:

| File | Content |
|---|---|
| `configmap.yaml` | Non-secret configuration, with `SHARED_STATE=mysql` and `TRUST_PROXY=1` |
| `secret.example.yaml` | Secrets template, to be copied to `secret.yaml` (excluded from git) |
| `deployment.yaml` | Two replicas, zero-downtime updates, probes, read-only filesystem, no privileges |
| `service.yaml`, `ingress.yaml` | Exposure on `catasto.example.org` (fictitious domain) |
| `pdb.yaml` | At least one pod running during node maintenance |

```bash
cp deploy/kubernetes/secret.example.yaml deploy/kubernetes/secret.yaml   # then fill it in
kubectl apply -k deploy/kubernetes        # on OpenShift: oc apply -k deploy/kubernetes
kubectl rollout status deployment/catasto
```

On **OpenShift** the container runs with a random UID in group `0`: the image supports this because it writes no files. The behaviour was verified by starting the server with an arbitrary UID. The `Ingress` is converted into a `Route`; alternatively, create the `Route` directly (comment in `ingress.yaml`). If the cluster cannot pull from Docker Hub, copy the image into the university's internal registry and update the name in `kustomization.yaml`.

In `kustomization.yaml`, pin the immutable tag published by CI (the commit's short SHA) rather than `latest`: a rollback becomes a tag change.

### 3.4 Virtual machine without containers

With Node.js 20 installed by the IT service:

```bash
git clone https://github.com/AntonioOrf/Catasto.git /opt/catasto && cd /opt/catasto
npm ci && npm run build
sudo cp deploy/systemd/catasto.service /etc/systemd/system/
sudo install -D -m 600 deploy/systemd/catasto.env.example /etc/catasto/catasto.env   # then fill it in
sudo systemctl daemon-reload && sudo systemctl enable --now catasto
```

The [`deploy/systemd/catasto.service`](../../deploy/systemd/catasto.service) unit applies the migrations before starting the server, restarts it on failure and makes the system read-only for the process. To update: `git pull && npm ci && npm run build && sudo systemctl restart catasto`.

### 3.5 Database provided by the university

The portal uses only standard MySQL 8 SQL (window functions, `REGEXP_REPLACE`, `GET_LOCK`). With **MySQL 8** or **TiDB** it works unchanged. With **MariaDB** or a different version, compatibility must be verified before the transfer by running the integration tests against a test database at the university:

```bash
TEST_DB_HOST=… TEST_DB_USER=… TEST_DB_PASSWORD=… TEST_DB_NAME=catasto_test \
  npm run test:integration -w catasto-backend
```

The test database name must contain `test`: the setup empties it.

## 4. Several instances

With a single instance (Docker Compose, one VM) nothing is needed. When the portal runs on several instances behind a load balancer (Kubernetes replicas, several VMs, Vercel) set `SHARED_STATE=mysql`:

| Aspect | With `SHARED_STATE` empty | With `SHARED_STATE=mysql` |
|---|---|---|
| Rate limiting | Per-instance counters: with N instances the real limit is N times the declared one | Counters in the `rate_limit_hits` table, shared by all instances |
| `POST /api/filters/cache/invalidate` | Clears the cache of the receiving instance only | The other instances catch up within 30 seconds |
| Migrations at startup | MySQL lock in any case: instances started together do not get in each other's way | Same |

No additional services are needed (Redis or similar): shared state uses the portal's database, with a few extra writes for each `/api` request. How it works is described in [Backend and API](backend.md), §4.3, §4.15 and §8.

## 5. Questions for the IT service

| Topic | Question | Why it matters |
|---|---|---|
| Platform | Virtual machine or container platform (Kubernetes, OpenShift)? With Docker or Podman? | Chooses the scenario in §3 |
| Database | Is the database managed by the university? MySQL 8, MariaDB or other? Who takes backups, and how often? | §3.5; contributed data (user reports, shelfmarks) exists only there |
| Domain and HTTPS | Who manages the domain and certificate? Is there a reverse proxy or load balancer in front? How many layers? | Value of `TRUST_PROXY` |
| Images | Can the server pull from Docker Hub, or is an internal registry required? | Image name in the deploy files |
| Outbound network | Are `archiviodigitale-icar.cultura.gov.it` and `formsubmit.co` reachable? Is an outbound proxy needed? | Folio viewer and user report emails |
| Email | Would a university SMTP server be preferred over FormSubmit? | Forwarding currently uses FormSubmit only: SMTP would need development |
| Updates | Do we apply updates ourselves (access to the machine or namespace) or does the IT service? | Release procedure |
| Monitoring | Is there a monitoring system to hook `/health/ready` into? Where do logs go? | The portal writes its logs to standard output |
| Personal data | Are there GDPR or retention requirements to meet? | User reports keep an IP hash and, optionally, an email |

## 6. Data transfer

1. On the current server, dump the database, with the application tables (`segnalazioni`, `fuoco_segnature`, `traduzioni_lookup`, `schema_migrations`) and their content:
   ```bash
   docker compose exec -T db sh -c 'mysqldump -u root -p"$MYSQL_ROOT_PASSWORD" --single-transaction --no-tablespaces --default-character-set=utf8mb4 "$MYSQL_DATABASE"' > catasto-$(date +%F).sql
   ```
   The file must end with `-- Dump completed`. If production uses TiDB, dump from there as in [Installation and deployment](installation.md), §3.7.
2. Import it into the university's database with `--default-character-set=utf8mb4`.
3. Start the portal: missing migrations are applied automatically.
4. Compare the row counts of the main tables with the source server, as in [Installation and deployment](installation.md), §3.7, then run the checks of §3.4 and `GET /health/ready`.
5. Suspend moderation during the switch: user reports accepted on the old server after the dump would be lost.

The dump contains personal data (IP hashes, reporters' optional emails): transfer it over an encrypted channel and delete it after the import.
